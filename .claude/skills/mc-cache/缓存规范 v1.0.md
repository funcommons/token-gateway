## 1. 概述

### 1.1 缓存的价值与代价

**价值**：
- 降低 DB 负载（QPS 10x+ 提升）
- 减少响应时间（μs vs ms 级）
- 节约成本（DB 容量）

**代价**：
- 数据一致性复杂
- 系统复杂度增加
- 缓存故障可能导致雪崩

### 1.2 缓存层级

```
L1: 本地缓存（Caffeine）     - μs 级，单机，受容量限制
L2: 分布式缓存（Redis）       - ms 级，集群，共享
L3: 持久化（PostgreSQL）      - 10ms+ 级，权威数据源
```

### 1.3 缓存适用判断

| 场景 | 适合缓存 |
|---|---|
| 读多写少（> 10:1） | ✅ |
| 数据稳定（修改频率低） | ✅ |
| 实时性要求不高 | ✅ |
| 强一致性要求 | ❌（直接走 DB） |
| 写多读少 | ❌（缓存意义不大） |
| 数据频繁变化 | ❌（一致性问题大） |

## 2. 基础缓存（Cache-Aside）

### 2.1 标准模式

```java
@Service
@RequiredArgsConstructor
public class OrderCacheService {

    private static final String ORDER_CACHE_PREFIX = "order:detail:v1:";
    private static final Duration ORDER_CACHE_TTL = Duration.ofMinutes(30);
    private static final Duration NULL_CACHE_TTL = Duration.ofSeconds(30);

    private final RedissonClient redissonClient;
    private final OrderMapper orderMapper;

    public OrderDetailVO getOrder(String orderId) {
        RBucket<OrderDetailVO> bucket = redissonClient.getBucket(ORDER_CACHE_PREFIX + orderId);
        OrderDetailVO vo = bucket.get();
        if (vo != null) return vo;

        // 防穿透：检查空对象标记
        RBucket<String> nullBucket = redissonClient.getBucket(ORDER_CACHE_PREFIX + "null:" + orderId);
        if ("NULL".equals(nullBucket.get())) {
            return null;
        }

        OrderDO order = orderMapper.selectById(orderId);
        if (order == null) {
            nullBucket.set("NULL", NULL_CACHE_TTL);
            return null;
        }

        vo = OrderConverter.toVO(order);
        bucket.set(vo, ORDER_CACHE_TTL);
        return vo;
    }

    @Transactional(rollbackFor = Exception.class)
    public void updateOrder(OrderDO order) {
        orderMapper.updateById(order);
        redissonClient.getBucket(ORDER_CACHE_PREFIX + order.getId()).delete();
        redissonClient.getBucket(ORDER_CACHE_PREFIX + "null:" + order.getId()).delete();
    }
}
```

### 2.2 Key 命名规范

| 规则 | 示例 |
|---|---|
| `[业务]:[子模块]:[版本]:[实体ID]` | `order:detail:v1:12345` |
| 加版本号便于 cache 失效 | `user:profile:v2:789` |
| Hash 表名：`[业务]:[类型]` | `session:web` |
| 列表：`[业务]:list:[排序]` | `order:list:hot:0` |

**禁用**：
- 超长 Key（< 100 字符）
- 含特殊字符（空格、换行）
- 直接用 entity JSON 作为 key

### 2.3 TTL 策略

| 数据特征 | TTL | 备注 |
|---|---|---|
| 高频访问热数据 | 5-30 min | 短，及时更新 |
| 中频数据 | 30 min - 2h | |
| 低频稳定数据（字典） | 1-7 day | |
| 会话 / Token | 与业务 TTL 对齐 | access 2h / refresh 30d |
| 空对象（防穿透） | 30s-5min | 防 DB 持续穿透 |
| 分布式锁 | 30s（业务最长 × 1.5） | 防死锁 |

**防雪崩**：基础 TTL ± 10% 随机抖动。

```java
private Duration randomTtl(Duration base) {
    long jitter = (long) (base.toMillis() * 0.1 * ThreadLocalRandom.current().nextDouble());
    return base.plusMillis(jitter);
}
```

### 2.4 序列化

**推荐**：Jackson（统一 mc-java-spec §4.6），配置如下：


## 3. 多级缓存（Caffeine + Redis）

### 3.1 Caffeine 本地缓存

```java
@Configuration
public class LocalCacheConfig {

    @Bean
    public Cache<String, OrderDetailVO> orderLocalCache() {
        return Caffeine.newBuilder()
            .maximumSize(10_000)                       // 容量上限
            .expireAfterWrite(Duration.ofMinutes(5))   // 写入后过期
            // .expireAfterAccess(Duration.ofMinutes(10))  // 访问后过期
            // .expireAfter(customExpiry)               // 自定义（按 value）
            .recordStats()                              // 统计
            .build();
    }
}
```

### 3.2 三级查询

```java
@Service
@RequiredArgsConstructor
public class OrderMultiLevelService {

    private final Cache<String, OrderDetailVO> localCache;
    private final RedissonClient redissonClient;
    private final OrderMapper orderMapper;
    private final MeterRegistry meterRegistry;

    public OrderDetailVO getOrder(String orderId) {
        Timer.Sample sample = Timer.start(meterRegistry);

        try {
            // L1: 本地缓存
            OrderDetailVO vo = localCache.getIfPresent(orderId);
            if (vo != null) {
                sample.stop(meterRegistry.timer("cache.get", "level", "l1", "result", "hit"));
                return vo;
            }

            // L2: Redis
            RBucket<OrderDetailVO> bucket = redissonClient.getBucket("order:detail:v1:" + orderId);
            vo = bucket.get();
            if (vo != null) {
                localCache.put(orderId, vo);    // 回填 L1
                sample.stop(meterRegistry.timer("cache.get", "level", "l2", "result", "hit"));
                return vo;
            }

            // L3: DB
            vo = loadFromDb(orderId);
            if (vo != null) {
                bucket.set(vo, Duration.ofMinutes(30));
                localCache.put(orderId, vo);
            }
            sample.stop(meterRegistry.timer("cache.get", "level", "l3", "result", vo == null ? "miss" : "load"));
            return vo;
        } catch (Exception e) {
            sample.stop(meterRegistry.timer("cache.get", "level", "error"));
            throw e;
        }
    }

    @Transactional(rollbackFor = Exception.class)
    public void update(OrderDO order) {
        orderMapper.updateById(order);
        // 失效多级
        redissonClient.getBucket("order:detail:v1:" + order.getId()).delete();
        localCache.invalidate(order.getId());
        // 广播失效
        redissonClient.getTopic("cache:invalidate:order").publish(order.getId());
    }

    @PostConstruct
    public void subscribeInvalidation() {
        // 各实例订阅失效广播
        redissonClient.getTopic("cache:invalidate:order")
            .addListener(String.class, (channel, orderId) -> {
                localCache.invalidate(orderId);
            });
    }
}
```

### 3.3 一致性窗口

L1 本地缓存接受短暂不一致（5-30 min 内）。如业务对此敏感：
- 减小 L1 TTL
- 用 Redis Pub/Sub 或 Kafka 广播失效（见上）
- 重大变更（如改价格）等几秒后再操作

## 4. 一致性策略

### 4.1 策略对比

| 策略 | 一致性 | 复杂度 | 适用 |
|---|---|---|---|
| **Cache-Aside** | 最终（弱） | 低 | 通用默认 |
| **延迟双删** | 接近强 | 中 | 强一致要求 |
| **Write-Through** | 强 | 高 | 写多读少 |
| **Write-Behind** | 最终（弱） | 高 | 写超高频 |
| **Binlog 订阅** | 最终（弱） | 中 | 强一致但解耦 |

### 4.2 Cache-Aside（旁路）

```
读：先查 Cache，miss 查 DB 并回填
写：先写 DB，后删 Cache（不要更新 Cache）
```

**为什么删除而非更新**：
- 更新可能并发顺序错乱（A 先 B 后被覆盖）
- 删除是幂等的
- 删除后下次读触发懒加载

### 4.3 延迟双删

针对「**写 DB 后，并发读回填脏数据**」问题：

```java
@Transactional(rollbackFor = Exception.class)
public void updateOrder(OrderDO order) {
    // 1. 先删缓存
    redissonClient.getBucket("order:detail:v1:" + order.getId()).delete();

    // 2. 写 DB
    orderMapper.updateById(order);

    // 3. 异步延迟再删（防并发读脏数据回填）
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);    // 主从延迟窗口
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }
        redissonClient.getBucket("order:detail:v1:" + order.getId()).delete();
    });
}
```

**延迟时间**：经验值 500ms-1s；根据主从延迟调整。

### 4.4 Binlog 订阅（强一致解耦）

```
应用写 DB → DB binlog → Canal → MQ → 消费 → 删 Cache
```

**优点**：应用无感知，强一致（binlog 是 DB 写入真相）。
**缺点**：架构复杂，需要 Canal / MQ。

### 4.5 实战陷阱

**陷阱 1：先删 Cache 再写 DB（错）**

```
T1: 删 Cache
T2: 读 Cache miss → 读 DB 旧值 → 回填 Cache
T1: 写 DB
结果：Cache 是旧值，DB 是新值
```

**修复**：用延迟双删。

**陷阱 2：写 Cache 失败未处理**

```java
// ❌ 阻塞业务
orderMapper.update(order);
redisTemplate.set(key, vo, ttl);  // 失败抛异常，事务回滚？

// ✅ 失败降级
orderMapper.update(order);
try {
    redisTemplate.delete(key);
} catch (Exception e) {
    log.error("Cache invalidation failed for {}", key, e);
    // 监控告警，不阻塞业务
}
```

**陷阱 3：缓存与 DB 事务不一致**

```java
@Transactional(rollbackFor = Exception.class)
public void update(OrderDO order) {
    redisTemplate.delete(key);  // 在事务内
    orderMapper.update(order);
    // 事务提交前，Cache 已删
    // 若其他线程读，会读到旧 DB 值
}
```

**修复**：删 Cache 放到事务后（`TransactionSynchronizationManager.registerSynchronization`）：

```java
@Transactional(rollbackFor = Exception.class)
public void update(OrderDO order) {
    orderMapper.update(order);

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                redisTemplate.delete(key);
            }
        }
    );
}
```

## 5. 三大经典问题

### 5.1 缓存穿透（Penetration）

**现象**：查询不存在的数据，每次穿透到 DB。

**解决方案**：

**A. 缓存空对象**

```java
public User getById(String id) {
    User user = redisTemplate.opsForValue().get("user:" + id);
    if ("NULL".equals(user)) return null;  // 空标记
    if (user != null) return user;

    user = userMapper.selectById(id);
    if (user == null) {
        // 缓存空对象，短 TTL
        redisTemplate.opsForValue().set("user:" + id, "NULL", Duration.ofMinutes(1));
        return null;
    }
    redisTemplate.opsForValue().set("user:" + id, user, Duration.ofMinutes(30));
    return user;
}
```

**B. 布隆过滤器**

```java
@PostConstruct
public void init() {
    bloomFilter = redissonClient.getBloomFilter("user:exists:bloom");
    bloomFilter.tryInit(1_000_000L, 0.01);  // 容量 100 万，1% 误判
    // 预热
    userMapper.selectAllIds().forEach(id -> bloomFilter.add(id));
}

public User getById(String id) {
    if (!bloomFilter.contains(id)) {
        return null;  // 一定不存在
    }
    // 走正常缓存流程
}
```

**新增数据时**：

```java
public void create(User user) {
    userMapper.insert(user);
    bloomFilter.add(user.getId());
}
```

**C. 接口层校验**：拒绝明显非法的 ID（负数、过长、格式错）。

### 5.2 缓存击穿（Breakdown）

**现象**：热点 key 过期瞬间，海量请求同时打 DB。

**解决方案**：

**A. 互斥锁**

```java
public OrderDetailVO getHotOrder(String orderId) {
    String cacheKey = "order:hot:" + orderId;
    OrderDetailVO vo = redisTemplate.opsForValue().get(cacheKey);
    if (vo != null) return vo;

    RLock lock = redissonClient.getLock("lock:order:hot:" + orderId);
    try {
        if (lock.tryLock(0, 10, TimeUnit.SECONDS)) {  // 不等待
            // 双重检查
            vo = redisTemplate.opsForValue().get(cacheKey);
            if (vo != null) return vo;

            vo = loadFromDb(orderId);
            redisTemplate.opsForValue().set(cacheKey, vo, randomTtl());
            return vo;
        }
        // 等不到锁，短暂等待后重试
        Thread.sleep(50);
        return getHotOrder(orderId);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new BizException(ErrorCode.SYSTEM_BUSY);
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
}
```

**B. 物理永不过期 + 异步刷新**

```java
public OrderDetailVO getHotOrder(String orderId) {
    OrderDetailVO vo = redisTemplate.opsForValue().get("order:hot:" + orderId);
    if (vo == null) {
        // 首次加载（同步）
        vo = loadFromDb(orderId);
        redisTemplate.opsForValue().set("order:hot:" + orderId, vo);
    } else if (isLogicallyExpired(vo)) {
        // 逻辑过期：异步刷新
        asyncRefresh(orderId);
    }
    return vo;  // 总是返回有值（即使旧）
}

private boolean isLogicallyExpired(OrderDetailVO vo) {
    return System.currentTimeMillis() - vo.getCachedAt() > 30 * 60 * 1000L;
}

@Async
public void asyncRefresh(String orderId) {
    RLock lock = redissonClient.getLock("lock:order:hot:refresh:" + orderId);
    if (lock.tryLock()) {
        try {
            OrderDetailVO fresh = loadFromDb(orderId);
            redisTemplate.opsForValue().set("order:hot:" + orderId, fresh);
        } finally {
            lock.unlock();
        }
    }
}
```

### 5.3 缓存雪崩（Avalanche）

**现象**：大量 key 同时过期，请求全打到 DB；或 Redis 宕机。

**解决方案**：

**A. 随机 TTL**：基础 TTL ± 10%（见 §2.3）。

**B. 多级缓存兜底**：Caffeine + Redis（见 §3）。

**C. 限流降级**：

```java
@HystrixCommand(fallbackMethod = "getOrderFallback")
public OrderDetailVO getOrder(String orderId) { ... }

public OrderDetailVO getOrderFallback(String orderId) {
    // 返回静态数据 / 默认值 / 抛友好错误
    return OrderDetailVO.defaultInstance();
}
```

或 Sentinel / Resilience4j。

**D. Redis 高可用**：哨兵 / 集群，主从切换 < 30s。

## 6. 热点 Key

### 6.1 识别

| 方法 | 命令 |
|---|---|
| Redis 内置（4.0+） | `redis-cli --hotkeys`（需 maxmemory-policy = allkeys-lfu） |
| 监控 | mc-monitor 场景一，看 QPS 分布 |

### 6.2 处理策略

**A. 本地缓存兜底**

见 §3 多级缓存。

**B. 多副本 Key**

```java
public OrderDetailVO getHot(String orderId) {
    int replica = ThreadLocalRandom.current().nextInt(REPLICA_COUNT);
    OrderDetailVO vo = redisTemplate.opsForValue().get("order:hot:" + orderId + ":" + replica);
    if (vo != null) return vo;

    vo = loadFromDb(orderId);
    // 写所有副本
    IntStream.range(0, REPLICA_COUNT).forEach(i -> {
        redisTemplate.opsForValue().set(
            "order:hot:" + orderId + ":" + i, vo, Duration.ofMinutes(10)
        );
    });
    return vo;
}
```

**C. 预热**

活动开始前，定时任务预加载：

```java
@Scheduled(cron = "0 */5 * * * ?")  // 每 5 分钟
@SchedulerLock(name = "hotKeyPreheat", lockAtMostFor = "PT4M")
public void preheatHotKeys() {
    List<String> hotIds = analyticsService.getHotOrderIds();
    hotIds.forEach(id -> {
        OrderDetailVO vo = loadFromDb(id);
        redisTemplate.opsForValue().set("order:hot:" + id, vo, Duration.ofMinutes(15));
    });
}
```

**D. 静态化**：CDN 缓存（如商品详情页 HTML）。

## 7. 分布式锁

### 7.1 Redisson 标准模板

详见 mc-java-spec §4.5。关键要点：

| 要点 | 说明 |
|---|---|
| `tryLock(waitTime, leaseTime, unit)` | 必配 |
| `finally unlock` + `isHeldByCurrentThread` | 防误删 |
| WatchDog 自动续期 | 默认每 10s 续到 30s |
| 业务时间 < leaseTime / 3 | 否则需禁 WatchDog 显式配 leaseTime |

### 7.2 进阶锁类型

**公平锁**（按请求顺序获取）：

```java
RLock fairLock = redissonClient.getFairLock("order:lock:" + orderId);
```

**读写锁**：

```java
RReadWriteLock rwLock = redissonClient.getReadWriteLock("config:rw");
RLock readLock = rwLock.readLock();    // 多读并发
RLock writeLock = rwLock.writeLock();  // 写独占
```

**联锁**（多 Redis 实例同时锁定）：

```java
RLock lock1 = redissonClient1.getLock("key1");
RLock lock2 = redissonClient2.getLock("key2");
RLock lock3 = redissonClient3.getLock("key3");

RedissonMultiLock multiLock = new RedissonMultiLock(lock1, lock2, lock3);
multiLock.lock();
try { /* ... */ } finally { multiLock.unlock(); }
```

### 7.3 禁用模式

**禁用 `SETNX + EXPIRE`**（非原子）：

```java
// ❌ 错误：SETNX 后崩溃，锁永远存在
jedis.setnx(key, value);
jedis.expire(key, 30);

// ✅ Redisson 已封装原子操作
```

**禁用 `DEL` 误删**：

```java
// ❌ 错误：可能删别人的锁
String value = jedis.get(key);
if (value != null) jedis.del(key);

// ✅ 用 Lua 脚本判断 + 删除（Redisson 已封装）
```

## 8. 限流（Redis + Lua）

### 8.1 算法对比

| 算法 | 特点 | 实现 |
|---|---|---|
| **固定窗口** | 简单，临界点突刺 | INCR + EXPIRE |
| **滑动窗口** | 平滑 | ZSET |
| **令牌桶** | 允许突发 | Lua + Hash |
| **漏桶** | 严格速率 | Lua + List |

### 8.2 滑动窗口（推荐）

```lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])     -- 窗口大小 ms
local threshold = tonumber(ARGV[3])  -- 最大请求数

-- 清除窗口外
redis.call('zremrangebyscore', key, 0, now - window)

local current = redis.call('zcard', key)
if current >= threshold then
    return 0
end

redis.call('zadd', key, now, now)
redis.call('pexpire', key, window)
return 1
```

```java
public boolean isAllowed(String resource, int threshold, Duration window) {
    Long allowed = redisTemplate.execute(
        new DefaultRedisScript<>(SLIDING_WINDOW_LUA, Long.class),
        List.of("rate:limit:" + resource),
        String.valueOf(System.currentTimeMillis()),
        String.valueOf(window.toMillis()),
        String.valueOf(threshold)
    );
    return allowed != null && allowed == 1;
}
```

### 8.3 Redisson RRateLimiter

```java
RRateLimiter limiter = redissonClient.getRateLimiter("rate:order:create");
limiter.trySetRate(RateType.OVER_ALL, 100, 1, RateIntervalUnit.SECONDS);

```

### 8.4 多维度限流

```java

// 单用户

}
```

## 9. 监控

### 9.1 核心指标

| 指标 | 公式 | 告警 |
|---|---|---|
| 命中率 | `hits / (hits + misses)` | < 80% |
| 内存使用 | `used_memory / maxmemory` | > 90% |
| 慢命令 | `slowlog_len` 增长率 | > 10/min |
| 连接数 | `connected_clients` | > 90% max |
| 复制延迟 | 主从延迟 ms | > 1s |
| Key 过期率 | `expired_keys / evicted_keys` | 异常增长 |

### 9.2 应用层监控

```java
@Service
@RequiredArgsConstructor
public class CacheMetrics {
    private final MeterRegistry registry;

    public <T> T withMetrics(String cacheName, String key, Supplier<T> supplier) {
        Timer.Sample sample = Timer.start(registry);
        String result = "hit";
        try {
            T value = supplier.get();
            if (value == null) result = "miss";
            return value;
        } catch (Exception e) {
            result = "error";
            throw e;
        } finally {
            sample.stop(registry.timer("cache.access",
                "cache", cacheName,
                "result", result
            ));
            registry.counter("cache.access.count",
                "cache", cacheName,
                "result", result
            ).increment();
        }
    }
}

// 使用
return cacheMetrics.withMetrics("order", orderId, () -> getOrderFromCache(orderId));
```

## 附录 A：缓存选型决策树

```
Q1: 数据是否需要强一致？
├── 是 → 不缓存，直接走 DB
└── 否 → 继续

Q2: 读 QPS > 1 万？
├── 是 → 多级缓存（Caffeine + Redis）
└── 否 → 单层 Redis

Q3: 数据更新频率？
├── 高（秒级）→ TTL 5-30 min，Cache-Aside
├── 中（分钟级）→ TTL 30min - 2h
└── 低（小时+）→ TTL 1-7 day

Q4: 是否热点？
├── 是 → 加互斥锁（防击穿）+ 多副本（防热 key）
└── 否 → 标准 Cache-Aside
```
