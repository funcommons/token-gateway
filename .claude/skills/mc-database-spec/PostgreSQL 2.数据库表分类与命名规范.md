# **PostgresSQL 数据库表分类与命名规范**

本文档整合了数据库表类型的专业分类与对应的命名规范，旨在提供一套完整、统一的设计标准。

## **1\. 引言**

在复杂的业务系统设计中，对数据库表进行合理的分类是至关重要的。这不仅有助于架构师和开发人员清晰地理解数据模型，还能指导数据库的物理设计（如索引策略、分区、冷热分离），从而在系统扩展性、可维护性和性能之间找到最佳平衡点。

本文档将常见的OLTP（在线事务处理）系统中的表归纳为七种核心类型，并详细阐述其功能、设计特点和应用场景。

## **2\. 命名基本原则**

1. **统一格式：** 必须使用小写字母、数字、下划线（\_）的组合。  
2. **模块前缀：** 表名必须以所属的业务模块名为前缀（如 ump\_, trade\_, sys\_），以便于归类和理解。  
3. **单数名词：** 核心表（实体表、事务表）必须使用**单数名词**，如 ump\_user，而非 ump\_users。  
4. **后缀区分：** 衍生表（如日志、统计、扩展表、配置表）必须在核心名词的基础上，使用**明确的后缀**来体现其表类型。

## **3\. 核心分类详情**

#### **3.1. 实体表 (Entity Tables) / 主数据表 (Master Data)**

* 核心功能 (Purpose)：  
  存储系统的核心业务对象或基础数据。它们是系统业务的“名词”，是其他业务数据所围绕的主体。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 中到大（如：千万级的用户表，百万级的商品表）。  
  * **数据稳定性：** 相对稳定。数据会缓慢增长（新增实体），更新操作（UPDATE）相对较少，删除操作（逻辑删除）更少。  
  * **主要操作：** 读操作（SELECT）远多于写操作。是 JOIN 查询中经常被关联的表。  
* **设计要点：**  
  1. **主键：** 必须有代理主键 id (如 bigserial / bigint)。  
  2. **唯一性：** 具有业务唯一性的字段（如 username, email）必须建立唯一索引（UK）。  
  3. **字段约束：** 核心字段应为 NOT NULL 并有合理的 DEFAULT 值。  
  4. **关联性：** 是被其他表（如事务表、关系表）频繁引用的“主表”。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[名词\]  
  * **说明：** 这是最基础的命名。使用代表核心业务对象的单数名词。  
* **常见示例 (Examples)：**  
  * ump\_user (用户表)  
  * trade\_product (商品表)  
  * crm\_customer (客户表)

#### **3.2. 事务表 (Transaction Tables)**

* 核心功能 (Purpose)：  
  记录业务过程中发生的具体事件、单据或任务。它们是系统业务的“动词”，是系统价值的核心。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 极大。随业务发展快速（甚至线性）增长。  
  * **数据稳定性：** 追加型（Append-only）。数据一旦写入，极少（甚至禁止）被更新（UPDATE），通常只会被查询或逻辑删除。  
  * **主要操作：** 写操作（INSERT）极其频繁。读操作（SELECT）通常按时间范围、主键ID或某个实体ID（如 user\_id）进行。  
* **设计要点：**  
  1. 通常是分库分表（Sharding）的主要对象。  
  2. 索引设计必须高效。除主键索引外，通常在关联的实体ID（user\_id, order\_id）和时间字段（created\_at）上建立索引。  
  3. 应避免复杂的 JOIN 查询，常采用“数据冗余”的设计来减少关联。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[名词\]  
  * **说明：** 与实体表规则相同。事务表（如订单、支付）也是其业务模块的核心名词。它们的区别在于业务特性（3.1 稳定，3.2 快速增长），而非命名。  
* **常见示例 (Examples)：**  
  * trade\_order (交易订单表)  
  * payment\_record (支付流水表)  
  * task\_queue (待办任务队列表)  
  * erp\_stock\_in\_document (入库单)

#### **3.3. 关系表 (Relation Tables) / 关联表 (Mapping)**

* 核心功能 (Purpose)：  
  维护两个或多个实体之间的关系，专用于解决多对多（M:N）的映射关系。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 中到大。取决于所关联实体的量级和关系的密集度。  
  * **数据稳定性：** 动态变化。关系的新增（INSERT）和解除（DELETE）都可能很频繁。  
  * **主要操作：** INSERT, DELETE 和 SELECT（通常作为 JOIN 的中间表）操作频繁。  
* **设计要点：**  
  1. 表结构极其简单，通常只包含两个（或多个）逻辑外键字段。  
  2. 必须为这两个（或多个）外键字段建立联合唯一索引（UNIQUE INDEX），以确保关系的唯一性，并极大优化查询性能。  
  3. 通常不需要单独的 id 主键，而是使用联合唯一索引作为逻辑主键。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[名词1\]\_\[名词2\]\_\[后缀\]  
  * **说明：** 为清晰地表示其“映射”功能，强烈推荐使用 \_rel (relation) 或 \_map (mapping) 作为后缀，以避免与实体表混淆。  
* **常见示例 (Examples)：**  
  * ump\_user\_role\_rel (用户角色关系表)  
  * cms\_article\_tag\_map (文章标签关系表)  
  * ump\_group\_member\_rel (群组成员关系表)

#### **3.4. 扩展表 (Extension Tables) / 属性表 (Attribute)**

* 核心功能 (Purpose)：  
  存储主实体的非核心属性，或用于解决未来不确定的字段扩展需求（EAV模型）。这是“垂直拆分”思想的体现。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 与主实体表保持一致（1:1 或 1:N）。  
  * **数据稳定性：** 动态，跟随主表。  
  * **主要操作：** 读写操作通常与主表绑定发生。  
* **设计要点：**  
  1. **一对一（1:1 或 1:0..1）关系设计：** 这是实现“垂直拆分”和“子类型继承”的通用物理模式。我们将其统一归类，但应在逻辑上加以区分：  
     * **A) 垂直拆分（扩展）：** 用于存放主实体的非核心、大字段（text, jsonb）或冷数据。这种情况下，主表的每一行 *通常都对应* 扩展表的一行（1:1）。  
     * **B) 子类型继承（继承）：** 用于实现“子类”对“父类”的属性继承。这种情况下，*只有部分* 主表行（父类）会在“继承表”（子类表）中有对应行（1:0..1）。  
  2. **EAV (实体-属性-值) 表：** 包含 entity\_id, attr\_key, attr\_value 三列。这种设计极度灵活，但也导致查询性能差、数据一致性难以保证。**应极度谨慎使用**，仅在属性完全无法预定义的场景（如电商SPU/SKU）下采用。  
* 命名规范与示例 (Naming Convention & Examples)：  
  此类型根据其不同的业务目的，有不同的命名方式。  
  * **规则 (A \- 垂直拆分)：** \[主表名\]\_\[后缀\]  
    * **说明：** 用于存放主表的冷数据或大字段。  
    * **后缀：** \_profile (资料), \_detail (详情), \_ext (扩展)  
    * **示例 (A)：**  
      * ump\_user\_profile (用户资料扩展表)  
      * trade\_product\_description (商品详情表)  
  * **规则 (B \- 子类继承)：** \[模块\]\_\[子实体名词\]\_\[父实体\]  
    * **说明：** 用于实现“子类”属性，表名本身即体现了其子类身份。（此规则已修正，以匹配示例）  
    * **示例 (B)：**  
      * ump\_company\_user (企业用户表，继承自 ump\_user)  
      * ump\_team\_user (团队用户表，继承自 ump\_user)  
  * **规则 (C \- EAV模型)：** \[模块\]\_\[主实体\]\_\[后缀\]  
    * **说明：** 用于存储主实体的动态键值对。  
    * **后缀：** \_attr, \_meta  
    * **示例 (C)：**  
      * trade\_goods\_attr (商品动态属性表)

#### **3.5. 配置表 (Configuration Tables) / 字典表 (Dictionary)**

* 核心功能 (Purpose)：  
  存储系统运行所需的静态配置、参数、枚举值或字典。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 小。  
  * **数据稳定性：** 极高（静态）。数据几乎不变，通常在系统初始化时载入，或由管理员在后台维护。  
  * **主要操作：** 读操作（SELECT）极其频繁，几乎无写入操作。  
* **设计要点：**  
  1. **缓存优先：** 数据应在应用启动时全量加载到内存缓存中（如 Redis 或 JVM 内存），避免频繁查询数据库。  
  2. **“代理主键 \+ 业务键”分离设计：**  
     * **代理主键 (PK):** 必须有一个业务无关的id (如 bigserial) 作为主键。  
     * **业务键 (UK):** 必须有一个业务相关的、可读的 code (如 dict\_code, config\_key) 字段，设为 NOT NULL UNIQUE。  
  3. **外部引用规范：** 其他业务表（如 users 表）在引用字典表时，**推荐** 引用 code (业务键) 而非 id (代理主键)。  
     * **理由 (可读性):** users.country\_code \= '+086' 的可读性远高于 users.country\_code\_id \= 123。  
     * **理由 (可移植性):** code 在所有环境（开发、测试、生产）中保持一致，而 id 可能会变化，导致数据迁移困难。  
     * **前提:** 此规范的前提是 code 字段一旦创建即视为**不可变 (Immutable)**。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[描述\]\_\[后缀\]  
  * **说明：** 使用描述性的名词，并配合 \_config 或 \_dict 后缀来标识。  
  * **后缀：** \_config (配置), \_dict (字典)  
* **常见示例 (Examples)：**  
  * sys\_global\_config (系统全局配置表)  
  * trade\_order\_status\_dict (订单状态字典表)  
  * base\_country\_code\_dict (国家代码字典表)

#### **3.6. 日志表 (Log Tables) / 流水表 (Journal)**

* 核心功能 (Purpose)：  
  记录系统运行日志、数据变更历史、用户操作轨迹或API调用记录。主要用于审计、安全和问题排查。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 极大。增长速度可能是所有表中第二快的（仅次于监控数据）。  
  * **数据稳定性：** 绝对的追加型（Append-only）。数据永不更新（UPDATE）或删除（DELETE）（除非归档）。  
  * **主要操作：** INSERT 操作极其频繁且并发高。读操作（SELECT）仅在排查问题或审计时低频发生。  
* **设计要点：**  
  1. **性能隔离：** 应尽量避免对业务主库造成写入压力。可考虑将日志写入消息队列（MQ），再由消费者异步批量写入日志库。  
  2. **存储优化：** 必须使用数据库分区（如按月或按天分区）。  
  3. **数据生命周期：** 必须有数据归档（Archive）策略，定期将冷数据迁移到低成本存储（如Hadoop, S3）。  
  4. 不应与业务表进行 JOIN 查询。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[主实体/业务\]\_\[后缀\]  
  * **说明：** 必须使用清晰的后缀来表明其日志/流水特性。  
  * **后缀：** \_log (日志), \_history (历史), \_journal (流水)  
* **常见示例 (Examples)：**  
  * ump\_user\_op\_log (用户操作日志)  
  * sys\_data\_change\_history (数据变更历史)  
  * gw\_api\_request\_log (API调用日志)

#### **3.7. 汇总表 (Summary Tables) / 统计表 (Statistics)**

* 核心功能 (Purpose)：  
  存储预先计算好的统计或聚合数据。这是用空间换时间的典型策略，用于优化复杂的报表和看板（Dashboard）查询。  
* **设计特点 (Characteristics)：**  
  * **数据量级：** 中到小。数据是聚合后的结果。  
  * **数据稳定性：** 定时更新。数据非实时，通过定时任务（如夜间批处理）从事务表、日志表中计算得来。  
  * **主要操作：** 写操作（INSERT ON CONFLICT UPDATE 或 TRUNCATE \+ INSERT）集中在定时任务时段。读操作（SELECT）在报表展示时非常频繁。  
* **设计要点：**  
  1. 数据（事实）+ 维度（Dimension）的设计。  
  2. 索引必须根据查询维度来建立（如按 date, user\_group, product\_category 建立联合索引），以确保报表查询性能极高。  
* **命名规范 (Naming Convention)：**  
  * **规则：** \[模块\]\_\[业务\]\_\[维度\]\_\[后缀\]  
  * **说明：** 必须使用后缀表明其统计属性，并常在名称中体现统计维度（如 daily）。  
  * **后缀：** \_stats (统计), \_summary (汇总), \_report (报表)  
* **常见示例 (Examples)：**  
  * trade\_daily\_sales\_report (日销售统计报表)  
  * ump\_user\_activity\_summary (用户日活跃汇总表)  
  * gw\_hourly\_api\_call\_stats (API小时调用统计)
