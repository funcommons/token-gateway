## 1. 概述

### 1.1 性能优化的三条铁律

1. **量化优先**：没有数据不优化。先压测、先监控、再优化
2. **二八原则**：80% 问题在 20% 代码。先找热点（DB > 远程调用 > 业务逻辑 > JVM）
3. **横向对比**：优化前后必须用相同基准测量，避免「感觉变快」

### 1.2 性能 SLA 基线

| 业务类型 | P99 | 可用性 | 适用示例 |
|---|---|---|---|
| 核心交易（资金相关） | ≤ 200ms | 99.95% | 下单、支付、退款 |
| 用户主流程 | ≤ 500ms | 99.9% | 登录、查询、提交 |
| 后台管理 | ≤ 1s | 99.5% | 列表、报表、批量 |
| 异步任务 | 不限 | 99% | 导出、对账、清理 |
| 静态资源 | ≤ 100ms | 99.9% | CDN 加速 |

## 2. 接口性能排查

### 2.1 五步定位法

```
1. 网关日志看接口总耗时
   ↓
2. APM/Trace 看分段（Controller / Service / DB / RPC / Cache）
   ↓
3. 数据库慢 SQL（Druid 监控）
   ↓
4. 外部依赖（Redis / RPC / 第三方 HTTP）
   ↓
5. JVM GC（jstat / Arthas）
```

### 2.2 常见瓶颈占比

| 瓶颈类型 | 占比 | 典型场景 |
|---|---|---|
| DB 慢 SQL | 60% | 缺索引、N+1、深分页 |

| 序列化 | 10% | 大对象 + JSON |
| GC | 8% | 频繁 YGC / Full GC |
| 锁竞争 | 5% | synchronized / 分布式锁等待 |

## 3. JVM 调优

### 3.1 JDK 17 推荐 JVM 参数

```bash
# 堆内存
-Xms4g -Xmx4g                          # 初始=最大，避免动态扩容
-XX:NewRatio=2                          # Young:Old = 1:2
-XX:SurvivorRatio=8                     # Eden:S0:S1 = 8:1:1

# GC（G1）
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200                # 目标停顿 200ms
-XX:G1HeapRegionSize=16m                # 大堆 16m/region
-XX:InitiatingHeapOccupancyPercent=45   # 老年代 45% 触发并发标记

# 元空间
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

# 直接内存
-XX:MaxDirectMemorySize=1g

# 异常诊断
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/heapdump.hprof
-XX:+ExitOnOutOfMemoryError             # OOM 时退出（容器重启）

# GC 日志
-Xlog:gc*:file=/var/log/gc.log:time,uptime:filecount=10,filesize=50m

# 容器感知（JDK 11+ 自动，但建议显式）
-XX:+UseContainerSupport
-XX:InitialRAMPercentage=75.0
-XX:MaxRAMPercentage=75.0
```

### 3.2 诊断工具

```bash
# 进程概览
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jstat -gcutil <pid> 1000 10           # 每秒一次共 10 次

# 堆 dump
jcmd <pid> GC.heap_dump /tmp/heap.hprof
# MAT / VisualVM 分析

# 线程
jstack <pid> > thread.dump

# Arthas
dashboard                              # 实时仪表盘
thread                                 # 线程
heapdump /tmp/heap.hprof               # 堆 dump
```

### 3.3 GC 调优目标

| 指标 | 目标 | 异常 |
|---|---|---|
| GC 占比 | < 5% | > 10% 需调优 |
| Full GC 频率 | < 1 次/天 | 每小时多次危险 |
| 单次 YGC | < 50ms | > 200ms 影响响应 |
| 单次 Full GC | < 500ms | > 2s 严重影响 |

### 3.4 常见 GC 问题

| 现象 | 原因 | 解决 |
|---|---|---|
| 频繁 YGC | 短命对象多 / Survivor 太小 | 调 `-XX:SurvivorRatio` |
| Full GC 频繁 | 老年代不足 / 内存泄漏 | 扩堆 / MAT 分析 |
| 单次 GC 长 | Region 太大 / Mixed GC | 调 `G1HeapRegionSize` |
| Stop-the-world 长 | CMS / Serial GC | 改 G1 / ZGC |

### 3.5 在线工具

- **GCEasy** (https://gceasy.io)：上传 gc.log，分析报告
- **MAT** (Eclipse Memory Analyzer)：堆 dump 分析
- **JFR** (Java Flight Recorder)：JDK 自带低开销 profiler

## 4. SQL 性能

### 4.1 EXPLAIN ANALYZE 速读

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID' ORDER BY created_at DESC LIMIT 20;
```

**优先看**：

| 节点 | 评价 |
|---|---|
| `Index Scan using idx_xxx` | ✅ 走索引 |
| `Index Only Scan` | ✅ 覆盖索引 |
| `Bitmap Heap Scan` | ⚠️ 大量行需检查 |
| `Seq Scan on 大表` | ❌ 全表扫描，需加索引 |
| `Sort` | ⚠️ 内存排序可能溢出磁盘 |
| `Hash Join` | ✅ 通常高效 |
| `Nested Loop` | ⚠️ 内表行数多时慢 |

**关键指标**：`cost`（启动 cost + 总 cost）、`rows`（预估行数）、`actual time`（实际耗时）、`Rows removed by filter`（过滤掉的行多 = 索引低效）。

### 4.2 索引设计

**复合索引顺序口诀**：等值在前、范围在中、排序在后。

```sql
-- ✅ 推荐：user_id 等值 + created_at 范围 + created_at 排序
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);

-- ✅ 覆盖索引：避免 heap fetch
CREATE INDEX idx_orders_user_created_covering
  ON orders (user_id, created_at DESC)
  INCLUDE (order_no, status, total_amount);

-- ✅ 部分索引：仅活跃数据
CREATE INDEX idx_users_active_email ON users (email) WHERE is_deleted = 0;

-- ✅ 表达式索引（如 mc-database-spec §6 提到的 EAV）
CREATE INDEX idx_goods_attr_weight ON goods (((attributes->>'weight')::numeric));
```

**禁用**：
- 全模糊 `LIKE '%xx%'`（用 PG `pg_trgm` 扩展或 ElasticSearch）
- 索引列运算 `WHERE date(created_at) = '2026-01-01'`（改 `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'`）
- 隐式类型转换（字符串列用数字查询）

### 4.3 SQL 优化清单

| # | 规则 |
|---|---|
| 1 | 只 SELECT 需要的列，禁 `SELECT *` |
| 2 | JOIN 不超过 3 表；多于用 CTE 拆 |
| 3 | IN 列表 ≤ 1000，超用 `= ANY(?)` 或临时表 |
| 4 | COUNT 大表用估算 `pg_class.reltuples` |
| 5 | 分页禁 OFFSET > 10000（详见 §6） |
| 6 | 避免子查询，用 JOIN / CTE |
| 7 | 复杂查询先 `EXPLAIN ANALYZE` |
| 8 | 写操作锁范围最小化 |

### 4.4 Druid 慢 SQL 监控

```yaml
spring:
  datasource:
    druid:
      filter:
        stat:
          slow-sql-millis: 2000        # 生产阈值
          log-slow-sql: true
```

告警规则（Prometheus）：

```promql
# 慢 SQL 次数 > 10/分钟
rate(druid_sql_slow_count[1m]) > 0.16

# SQL 平均耗时 > 500ms
druid_sql_execute_avg_ms > 500
```

### 4.5 案例：从 8s 到 50ms

**问题**：`SELECT * FROM orders WHERE DATE(created_at) = '2026-01-01'`

**诊断**：Seq Scan on 1000 万行表，DATE 函数阻止用索引。

**修复**：

```sql
-- 1. 改写
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';

-- 2. 加索引
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- 3. 复核
EXPLAIN ANALYZE ...
-- Index Scan, 8s → 50ms
```

## 5. N+1 检测与修复

### 5.1 反模式识别

```java
// ❌ N+1：每条订单查一次用户
List<OrderDO> orders = orderMapper.selectList(...);
for (OrderDO order : orders) {
    UserDO user = userMapper.selectById(order.getUserId());  // N 次！
}
```

### 5.2 修复方案

**方案 A：批量查询 + Map 映射**（最常用）

```java
List<OrderDO> orders = orderMapper.selectList(...);
Set<Long> userIds = orders.stream().map(OrderDO::getUserId).collect(Collectors.toSet());

Map<Long, UserDO> userMap = userMapper.selectBatchIds(userIds).stream()
    .collect(Collectors.toMap(UserDO::getId, Function.identity()));

List<OrderListItemVO> result = orders.stream()
    .map(o -> {
        OrderListItemVO vo = toVO(o);
        vo.setUserName(userMap.get(o.getUserId()).getName());
        return vo;
    })
    .toList();
// 2 次 SQL（1 次订单 + 1 次用户批量）
```

**方案 B：MyBatis 关联查询**

```xml
<resultMap id="orderWithUser" type="OrderListItemVO">
    <association property="user" javaType="UserVO"
                 select="com.example.mapper.UserMapper.selectById"
                 column="user_id"/>
</resultMap>

<select id="selectOrders" resultMap="orderWithUser">
    SELECT * FROM orders WHERE ...
</select>
```

> ⚠️ 注意：嵌套 select 是 N+1 重灾区，必须配 `lazy-loading-enabled + default-batch-fetch-size`：

```yaml
mybatis-plus:
  configuration:
    lazy-loading-enabled: true
    default-batch-fetch-size: 100   # 一次批量 100 条
```

**方案 C：JOIN 一次性查**

```xml
<resultMap id="orderWithUser" type="OrderListItemVO">
    <result property="id" column="o_id"/>
    <result property="orderNo" column="o_order_no"/>
    <association property="user" javaType="UserVO">
        <result property="id" column="u_id"/>
        <result property="name" column="u_name"/>
    </association>
</resultMap>

<select id="selectOrders" resultMap="orderWithUser">
    SELECT o.id o_id, o.order_no o_order_no, u.id u_id, u.name u_name
    FROM orders o
    LEFT JOIN users u ON o.user_id = u.id
    WHERE ...
</select>
```

### 5.3 自动检测

```java
@Test
void test_no_n_plus_one() {
    // given: 准备 10 条订单
    IntStream.range(0, 10).forEach(i -> createOrder());

    // when
    var list = service.listOrders(...);

    // then: 验证 SQL 次数
    assertThat(getSqlExecutions())
        .extracting(SqlExecution::getSql)
        .filteredOn(s -> s.contains("FROM orders"))
        .hasSize(1);
}
```

## 6. 深分页

### 6.1 问题：OFFSET 越大越慢

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 1000000;
-- DB 仍要扫描 1000020 行，丢弃前 100 万
```

### 6.2 解决方案

**方案 A：Keyset 分页（推荐，详见 mc-api-spec v1.6 §6.4）**

```sql
-- 第一页
SELECT id, created_at, ... FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 后续页（基于上一页最后一条记录）
SELECT id, created_at, ... FROM orders
WHERE (created_at, id) < ('2026-06-01 12:00:00', '892310293')
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**复合排序键索引**：

```sql
CREATE INDEX idx_orders_created_id ON orders (created_at DESC, id DESC);
```

**方案 B：Cursor 分页（详见 v1.6 §6.3）**

服务端用游标字符串封装 `last_value + last_id`，客户端 opaque 传回。

**方案 C：估算总数**

`COUNT(*)` 大表代价高，用 PG 估算：

```sql
SELECT reltuples::bigint AS total FROM pg_class WHERE relname = 'orders';
```

或单独维护计数表，异步更新。

**方案 D：业务限制**

后台管理：默认仅显示前 1000 条，要求用户加搜索条件。

### 6.3 实战对比

| 方案 | LIMIT/OFFSET 100 万行 | Keyset |
|---|---|---|
| 耗时 | 8s | 50ms |
| SQL 次数 | 1 | 1 |
| 索引要求 | (created_at) | (created_at, id) |
| 跳页 | ✅ | ❌ 仅下一页 |

### 10.2 脚本模板

```js
import http from 'k6/http'
import { check, sleep } from 'k6'
import { Rate, Trend } from 'k6/metrics'

const errorRate = new Rate('errors')
const orderCreateLatency = new Trend('order_create_latency')

export const options = {
  stages: [
    { duration: '2m', target: 100 },     // 2 分钟升到 100 VU
    { duration: '5m', target: 100 },     // 持续 5 分钟
    { duration: '2m', target: 500 },     // 升到 500 VU
    { duration: '5m', target: 500 },     // 持续
    { duration: '2m', target: 0 }        // 降到 0
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],    // P99 < 500ms
    errors: ['rate<0.01']                // 错误率 < 1%
  }
}

export default function () {
  const res = http.post('https://api.example.com/v1/orders', JSON.stringify({
    sku: 'SKU001', quantity: 1
  }), {
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${__ENV.TOKEN}`,
      'Idempotency-Key': Math.random().toString(36)
    }
  })

  orderCreateLatency.add(res.timings.duration)

  const ok = check(res, {
    'status is 200': r => r.status === 200,
    'code is 0': r => r.json('code') === 0,
    'has trace_id': r => r.json('trace_id') !== null
  })

  errorRate.add(!ok)
  sleep(0.5)
}
```

### 10.3 场景设计

| 场景 | 目的 | 配置 |
|---|---|---|
| 容量压测 | 找最大 QPS | 阶梯加压到 500/1000/2000 VU |
| 极限压测 | 看崩溃临界点 | 持续高 QPS 30-60min |
| 稳定性压测 | 8h 跑 80% 容量 | 单一高 QPS 长期 |
| 突发压测 | 瞬时 10x | 1 秒内 0 → 1000 VU |
| 浸泡测试 | 内存泄漏 | 24h 50% 容量 |

### 10.4 关键指标

## 11. SLO 与错误预算

### 11.1 SLI / SLO / SLA 定义

| 层 | 含义 | 示例 |
|---|---|---|
| **SLI**（指标） | 服务质量量化指标 | P99 响应时间、可用性 % |
| **SLO**（目标） | 内部对 SLI 的目标 | P99 ≤ 200ms，可用性 ≥ 99.9% |
| **SLA**（协议） | 对外承诺（违约赔款） | 可用性 ≥ 99.5%（< 则退款） |

### 11.2 错误预算

可用性 99.9% → 每月允许 43.2 分钟不可用。

| 可用性 | 每月允许不可用 | 适合场景 |
|---|---|---|
| 99% | 432min（7.2h） | 内部工具 |
| 99.5% | 216min（3.6h） | 一般业务 |
| 99.9% | 43min | 核心业务 |
| 99.95% | 21.6min | 资金 / 交易 |
| 99.99% | 4.3min | 高度关键 |

### 11.3 燃烧率告警

```promql
# 1 小时燃烧 2% 错误预算 → 立即告警（P1）
(
  sum(rate(http_requests_failed[1h])) / (1 - 0.999) > 14.4
)
and
(
  sum(rate(http_requests_failed[5m])) / (1 - 0.999) > 14.4
)

# 6 小时燃烧 5% 错误预算 → 告警（P2）
(
  sum(rate(http_requests_failed[6h])) / (1 - 0.999) > 6
)
```

详见 mc-monitor。
