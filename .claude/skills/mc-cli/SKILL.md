# mc-cli：交互式指令执行流程

## 0. 用户速查

| 你想 | 输入 |
|---|---|
| 激活 | `/mc-cli <你的需求>` |
| 快速通过 | 「全部按默认」/「确认」/「go」 |
| 改方案 | 「换方案」或描述新要求 |
| 跳过流程 | 「跳过确认」（不可逆动作仍保护） |
| 中止 / 退出 | 「停」/「退出 mc-cli」 |

## 1. 元信息

| 项 | 说明 |
|---|---|
| 类型 | 流程编排（meta-skill），非业务规范 |
| 激活 | 手动 `/mc-cli`；由 Skill 调度器保证，本 SKILL 无需自检激活条件 |
| 优先级 | Claude Code plan mode **>** mc-cli **>** 默认行为 |
| 落地工具 | `AskUserQuestion`（Phase 3 / 多方案 Phase 5 / 二次确认首选） |
| 与业务规范 | mc-cli 是流程框架，业务规范是方案内容来源 |

## 2. 核心原则

> **执行前必须确认。不可逆动作必须二次确认。**

**任务类型分类**（决定流程强度）：

| 类型 | 示例 | 流程强度 |
|---|---|---|
| 只读 | Read / Grep / Glob / WebSearch | 不确认 |
| 本地修改 | Edit / Write 本地文件 | Phase 5 方案确认 |
| 本地命令 | `mvn compile` / `npm test` | Phase 5 方案确认 |
| 不可逆 | `rm` / `git push --force` / `DROP TABLE` | Phase 5 + 二次确认 |
| 外部通信 | Slack / Webhook / 邮件 | Phase 5 + 二次确认 |

## 3. 六阶段工作流程

```
Phase 1: 意图分析     → 拆解动词/对象/约束/期望/歧义（内部思考）
   ▼
Phase 2: 置信度评估   → 默认进 Phase 3；4 项全清晰才跳过
   ▼
Phase 3: 理解求确认   → AskUserQuestion（意图层：「我理解对了吗」）
   ▼ （用户确认）
Phase 4: 方案设计     → 步骤 / 影响文件 / 风险 / 验证 / 估时档位
   ▼
Phase 5: 方案求确认   → 单方案文本；多方案 AskUserQuestion（方案层：「这样做可以吗」）
   ▼ （用户确认）
Phase 6: 执行         → 不可逆动作二次确认；失败回滚；末尾输出执行报告
```

> **Phase 3 vs Phase 5**：前者确认「理解对了吗」（意图层），后者确认「这样做可以吗」（方案层）。

### Phase 1：意图分析（内部，不输出）

拆解：动词 / 对象 / 约束 / 隐含期望 / 上下文依赖 / 歧义点。

### Phase 2：置信度评估（保守原则）

**默认进入 Phase 3**。仅当**同时满足全部 4 项**才跳过：

1. 动词单一明确（查询 / 列出 / 读取）
2. 对象路径/名称完全指定
3. 不涉及修改 / 删除 / 外部副作用
4. 不依赖外部上下文

**犹豫时进 Phase 3，宁严勿松。** 歧义信号：模糊代词（这个/那个）、多动词歧义、缺约束、依赖外部上下文、领域术语未定义、多种合理实现、影响范围不明、隐含副作用。

### Phase 3：结构化理解求确认

**工具**：`AskUserQuestion`。输出理解表（目标/对象/范围/期望产出/隐含约束/不包括）+ 歧义点表（# / 歧义 / 默认选择 / 备选），请用户回应「全部按默认」/ 逐条回答 / 完全不同的理解。

### Phase 4：方案设计

| 维度 | 内容 |
|---|---|
| 步骤 / 文件 / 工具 / 风险 / 验证 | 拆成可独立验证的步骤；列出每个要改/创建/删除的文件；标注是否含不可逆动作；如何确认成功 |
| 估时档位 | **XS**（<1min，单次 Edit）/ **S**（1~10min，局部）/ **M**（10~60min，多文件）/ **L**（>60min，建议拆分多个 SKILL 调用） |

### Phase 5：方案求确认

**单方案**（推荐度 ≥ 70%）：文本表格输出步骤（含工具、影响文件、类型）+ 风险与验证 + 估时档位，请求确认。

**多方案**（推荐度接近）：用 `AskUserQuestion`。判定「推荐度接近」的客观信号（命中任一）：
- 多方案在不同维度各占优势
- 多方案都符合现有规范
- 方案对比 3+ 维度分布不集中
- 业务场景未明确

可在 Phase 5 内继续 `AskUserQuestion` 补充提问，不必回 Phase 3。

### Phase 6：执行

**行为**：每步进度回报；只读动作连续执行无需逐步确认；本地修改按方案自动执行；**不可逆动作必须二次确认**；偏离方案立即停下回 Phase 5。

**不可逆动作清单**：文件删除（`rm` / `git clean -fd`）/ Git 危险（`push --force` / `reset --hard` / `branch -D`）/ 数据库破坏（`DROP` / `TRUNCATE` / 无 WHERE 的 `DELETE`）/ 共享状态（推送、合并 PR、发版）/ 外部通信（Slack / 邮件 / Webhook）/ 基础设施（CI/CD / K8s / DNS）/ 依赖破坏（`purge` / 删 lock）/ 凭证权限（API Key / Token / SSH Key）。

**二次确认**（`AskUserQuestion`）：输出动作 / 影响 / 可逆性，请用户回「确认执行」/「取消」。

**失败处理**：立即停止后续步骤；输出失败报告（失败步骤 / 错误信息 / 已执行 / 已影响）；提供「重试 / 跳过 / 回滚 / 停」四选项；不擅自继续。

**执行报告**（强制输出）：步骤结果表 + 影响文件 + 下一步建议。

## 4. 例外与多轮对话

| 用户输入 | 行为 | 不豁免 |
|---|---|---|
| `跳过确认` / `直接做` / `stop asking` | 跳过 Phase 3/5 | Phase 6 不可逆动作二次确认 |
| `退回` / `换个方案` | 回 Phase 1 或 Phase 4 | - |
| `停` / `取消` | 立即停止 | - |
| `退出 mc-cli` | 关闭流程，回默认行为 | - |

> 「跳过确认」= 信任 Claude 的方案设计，**但不可逆动作始终保护**，绝非完全自主。

**多轮对话**：同一 SKILL 会话内每条新指令重新走 Phase 1，但可引用之前上下文（如「按刚才的方案改 X」）。

## 5. 反例（避免）

**❌ 不分析直接做**：用户「修一下登录 bug」→ Claude 立即改代码。正确：Phase 2 命中「缺约束」→ Phase 3 求确认。

**❌ 自信地误读**：用户「优化这个查询」→ Claude 自信加索引。正确：Phase 2 命中「模糊代词」+「多动词歧义」→ Phase 3 列出可能对象。

**❌ 跳过确认后乱搞**：用户「跳过确认」→ Claude 执行 `rm -rf`。正确：跳过仅豁免 Phase 3/5；不可逆动作清单**始终生效**。

**❌ 用户错误用法**：用户 `/mc-cli 跳过确认，rm -rf /` → Claude 必须**拒绝并警示**，不可执行极端危险命令。

## 6. 进度输出（强制）

每个 Phase 切换时输出一行进度（替代内部自检清单，对外可见）：

```
[Phase 1→2] 命中 1 项歧义 → 进 Phase 3
[Phase 3→4] 用户：全部按默认 → 方案设计
[Phase 5→6] 用户：go → 开始执行
[Phase 6]   步骤 2/3 完成：Edit yyy.java
```

## 附录：示例

### 示例 1：清晰指令（满足跳过条件）

```
用户：/mc-cli 列出 mc-api-spec/*.md

[Phase 1→2] 4 项全清晰 → 跳 Phase 3
[Phase 5]   | 步骤 | 动作 | 工具 | 类型 |
            |---|---|---|---|
            | 1 | 列出 | Glob | 只读 |
            估时 XS。确认后执行。
[Phase 5→6] 用户：go
[Phase 6]   Glob 返回 6 个文件

✅ 完成：6 个 .md 文件
```

```
用户：/mc-cli 给订单列表加分页

[Phase 1→2] 命中「多动词歧义」（分页方式未指定）→ Phase 3
[Phase 3]   AskUserQuestion：业务场景？
            - 后台管理（默认）
            - Feed 流
            - 大数据量
用户：Feed 流

[Phase 4→5] 方案：Cursor 分页（v1.6 §6.3），单文件，估时 S
[Phase 5→6] 用户：确认
[Phase 6]   Edit OrderController.java

✅ 完成：Cursor 分页已实现。下一步：mvn test 验证
```
